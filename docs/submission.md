# 도란 1차 제출 준비

이 문서는 제출 산출물과 최종 확인 절차를 설명한다. 실제 검증 상태는 [검증 기록](verification.md)을 따른다.

## 제출 산출물

| 산출물 | 포함할 내용 |
|---|---|
| GitHub | 제출 기준 커밋, 전체 소스, 실행 방법, 테스트 환경, 필요한 설정 |
| 차량 APK | 서명된 실행 가능한 release 빌드, 저장소 `apk/` 폴더 |
| 모바일 APK | 같은 서버 계약을 사용하는 Android release 빌드 |
| 화면 녹화 | 실제 설치 앱의 음성 대화·기록 저장·수정 보호·삭제 반영 |
| 검증 자료 | 확인된 동작, 미확인 조건, 앱·서버 버전, 파일 SHA-256 |

공식 제출 안내는 release APK와 소스, 최종 커밋 번호, Pleos Connect 에뮬레이터 버전·화면 규격을 요구한다. APK·영상이 저장소 업로드 한도를 넘으면 GitHub Releases 경로를 사용한다. [공식 제출 안내](https://appdevchallenge.auto-hmg.io/guide/submission)

현재 크기의 APK는 공식 안내의 `apk/` 폴더에 넣는다. 시연 영상은 GitHub Release의 첨부 파일로 제공하고 README에 내려받기 링크를 적는다. GitHub는 일반 Git 파일이 100MiB를 넘으면 차단하므로 `demo/*.mp4`는 Git에서 제외한다. 포장된 영상 파일은 로컬 `demo/`에 보관한다. [GitHub 파일 크기 제한과 Releases](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

팀명 확정 전 빌드 보관 이름은 `doran-car-release.apk`, `doran-mobile-release.apk`를 사용한다. 실제 제출 시 차량 APK를 공식 형식인 `팀명_도란_release.apk`로 정리한다. 파일명만 변경해도 SHA-256은 동일하지만 최종 목록의 경로는 다시 확인한다.

현재 검증한 차량·모바일 release APK 빌드와 독립 공개 검사를 마쳤다. 모델 직접 평가, 별도 debug 앱의 최초 합성 PCM 1회·후속 3회 및 내비 경로 1회 관측을 기록했다. 현재 차량 `b73fbd34…`는 정상 TTS 완료 뒤 불필요한 stop을 제거한 `4cbe3aa` 소스이며, JVM 49개 시험·정적 검사·빌드·CI·공개 검사를 통과했다. 추가로 고립 Room·Keystore 영속성, 같은 UID의 통화 용도 오디오 포커스 손실, 이전 `1271d0d1…` release 합성 탭 1회의 화면 피드백 관측 상한 185ms를 확인했다. 내비 용도 포커스 요청은 플랫폼이 거절했다. 이전 차량 `1271d0d1…`의 최초 업데이트 계측과 같은 파일의 깨끗한 설치는 해당 버전의 증거로 보존한다. 이 계측은 제출 release의 사람 음성 시연을 대신하지 않는다. Android 실제 Google 로그인과 모바일·차량 양쪽 승인 연결, claimed 상태 재부팅 복원, 연결 완료 후 대화 시작 전 화면의 가상 주행·분할 대응을 확인했다. 이 과정에서 마이크나 AI 대화는 시작하지 않았다. iOS도 첫 인증 오류 후 재로그인과 같은 차량 조회를 확인했다. 첫 사람 발화 4턴은 서버 응답·종료 후 기록/일기 생성까지 관측했으나 지연·잡음·TTS 실패가 있었다. 수정 후 재시험 3주기에서 TTS 완료 6회·실패 0회를 관측했으나 사용자 잡음·지연은 남아 있다. iOS에서는 개별 기록 3개·AI 일기 본문과 편집 화면을 저장 없이 확인했다. Android 본문 조회, 수정 저장·보호·비교·삭제, 사람 20턴 연속 발화와 제출 영상은 별도로 완료해야 한다. 최신 해시와 관측 범위는 [검증 기록](verification.md)을 확인한다. APK가 생성됐다는 사실만으로 제출 패키지가 완료된 것은 아니다. 연결 코드 복원이 추가된 최신 차량 APK와 이전 UI·SDK 시험 파일의 버전을 구분하며, 최종 녹화에는 고정한 제출 APK를 사용한다.

최신 `183dd4c` 소스의 CI·65개 모바일 시험과 두 플랫폼 재빌드를 완료했다. 새 Android `d4dba0f6…`는 깨끗한 설치 후 기존 Google 세션 SSO와 연결 차량 1개 조회를 확인했다. 이전 `59a42829…`의 양쪽 승인·로그아웃 증거는 보존하며 새 pairing 실행으로 계산하지 않는다. iOS 새 Runner는 업데이트·설치 파일 일치 이후 실제 재로그인·같은 차량 조회까지 확인했다. 실제 저장값·세션 보존은 측정하지 않았다. 최종 제출은 이 산출물로 남은 대화·기록 흐름과 영상을 확인한 뒤 고정한다.

## 약 3분 시연 구성

1. **서비스와 상태 소개:** 차량에서 이야기하고 휴대폰에서 기록을 다듬는 용도를 설명한다. Pleos 에뮬레이터·예시 기록임을 표시한다.
2. **대화 이어가기:** 과거 발표 이야기를 참고하는 실제 대화와 사용자의 정정을 보여준다. 음성 상태와 일시정지·종료 조작을 포함한다.
3. **자동 기록과 연동:** 대화를 종료하고 모바일에서 새 개별 기록과 갱신된 하루 일기를 확인한다.
4. **내 글 보존:** 직접 수정한 하루 일기가 새 AI 초안과 분리되어 유지되는 과정을 보여준다.
5. **기록 통제:** 개인화 제외 또는 삭제 후 화면과 이후 대화에 반영되는 동작을 보여준다.

핵심 흐름에는 무편집 구간을 포함한다. 합성 발화, 미리 준비한 과거 기록, 가상 차량 신호를 사용한 경우 표시한다. 편집으로 응답 지연이나 실패를 숨기지 않는다. Google 계정 정보·연락처·키·개발자 도구의 비밀값은 영상에 노출하지 않는다.

## 최종 고정 절차

- 모든 release 시험이 끝난 뒤 제출 기준 커밋을 고정한다.
- 영상에 사용한 APK와 제출 APK가 같은 파일인지 SHA-256으로 확인한다.
- README에 APK 경로, 실제 지원 범위, 온라인 서비스에 필요한 설정을 연결한다.
- 공유 링크를 새 세션에서 열어 접근 가능 여부와 파일 다운로드를 확인한다.
- 공개 검사기 실행 후 스크린샷·영상·라이선스를 수동 확인한다.
- 완료하지 못한 기능이나 미검증 환경은 그대로 명시한다. 기획상의 기능을 실제 구현 결과로 표현하지 않는다.

검증한 소스·문서를 먼저 커밋하고, 저장소 루트에서 다음 명령으로 산출물을 묶는다. 경로와 팀명은 실제 값으로 바꾼다. 빌드나 화면 녹화를 대신 생성하는 명령이 아니다.

```sh
python3 scripts/package-release.py \
  --car-apk /absolute/path/to/car-release.apk \
  --mobile-apk /absolute/path/to/mobile-release.apk \
  --video /absolute/path/to/doran-demo.mp4 \
  --team 확정팀명 \
  --version 1.0.0
```

도구는 소스 작업 폴더의 변경 여부, 기존 출력 충돌, APK 공개 검사, 영상 길이를 확인한 뒤 `apk/`, `demo/`, `release-manifest.json`을 생성한다. manifest에는 `release_version`과 파일 해시가 들어가며, 영상에는 `distribution=release_asset`과 업로드할 `asset_name`을 기록한다. `source_commit`은 포장 시 소스 커밋이므로, 해당 커밋으로 빌드·시연했다는 별도 검증을 완료해야 한다. APK와 manifest를 추가 커밋하여 최종 제출 커밋을 고정하고, 이 커밋을 가리키는 GitHub Release에 `demo/doran-demo.mp4`를 첨부한다. 업로드 파일을 다시 내려받아 manifest의 SHA-256과 일치하는지 확인하고 Release 링크를 제출 자료에 넣는다. 영상 내용·개인정보·실제 앱 흐름의 수동 검토와 APK 서명 검사는 이 명령이 대신하지 않는다.

팀명이 미정이면 `--team 확정팀명` 대신 `--provisional-team`을 사용한다. 이 경우 APK 이름은 `doran-car-release.apk`, `doran-mobile-release.apk`이며 manifest의 `team_name`은 null, `naming_status`는 `provisional`로 남긴다. 실제 접수 전 팀명이 정해지면 공식 파일명으로 변경하고 manifest의 경로·팀명을 갱신한다. 파일 내용이 같으면 SHA-256은 유지된다.

공모전 이메일 접수는 앱 제작과 별도 작업이다. 제출용 신청서·서명·개인 연락처와 팀 내부 대화는 공개 저장소에 넣지 않는다.
