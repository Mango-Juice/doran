# 도란 음성 시험과 제출 영상 리허설

이 문서는 **실행할 절차와 가상 발화 예시**다. 작성·검토했다는 사실은 시험 통과나 실제 녹화의 증거가 아니다. 실제 결과는 앱·서버 버전, APK 해시, 실행 시각과 함께 [검증 기록](verification.md)에 따로 남긴다. AI 답변은 미리 정하거나 다른 음성으로 대체하지 않는다.

## 준비와 이전 기록 만들기

모든 이야기는 공개 시연을 위해 만든 가상 사례다. 실제 일정·프로젝트·취향·직장·주소·연락처를 넣지 않는다. 정차한 Pleos 에뮬레이터에서 사람이 실제 마이크로 말한다. 차량 신호를 가상으로 입력했다면 화면에 그 사실을 표시한다. 좌석 정보가 없을 때 실제로 혼자인 경우에만 앱의 혼자 대화 확인을 사용한다.

Google 로그인, 차량 연결, 마이크 권한과 처리 동의는 녹화 전에 마친다. 개인화는 시험자가 동의한 상태에서 켠다. 계정과 기존 기록을 확인하여 아래에서 삭제할 **가상 시험 기록만** 구별한다. 전체 과정은 가능하면 같은 KST 날짜에 진행한다. 자정을 넘겼다면 각 기록과 일기의 날짜부터 확인한다.

1. 차량 앱에서 새 대화를 시작한다. 다음 두 문장을 각각 말하고 실제 응답을 기다린다.
   - “가상 시연 사례를 이야기할게요. 내일 오후 세시에 파란 노트라는 가상 프로젝트를 발표할 예정이에요.”
   - “발표 자료는 세 장으로 준비하려고 해요. 아직 발표를 한 건 아니에요.”
2. 차량의 종료 버튼으로 마무리한다. 모바일에 **이전 기록 A**와 AI 하루 일기가 생길 때까지 기다린다. 생성이 지연되거나 실패하면 그 상태를 기록하며 직접 DB에 내용을 넣어 성공처럼 만들지 않는다.
3. 모바일 `오늘`의 하루 일기를 열어 직접 다음 문장으로 다듬고 저장한다. “시연용으로 직접 쓴 일기입니다. 발표 시간을 다시 확인하고 차분하게 준비하고 싶습니다.” 이 문장을 **수정본 M**으로 기록한다. 저장 후 화면을 다시 열어 같은 글이 보이는지 확인한다.
4. 차량에서 새 대화를 시작한다. 아래 20개 대화 발화와 별도의 21번째 종료 제어 발화는 이 **한 세션**에서 이어간다. 세션 시작 이후 앱을 다시 열거나 대화를 새로 시작한 결과를 이어 붙이지 않는다.

## 사람 발화 20턴 본시험

앱이 듣기 상태로 돌아온 뒤 다음 발화를 말한다. 각 턴에서 인식된 문장, 응답 시작까지의 실제 대기, TTS의 첫 음절·끝 음절, 응답 후 듣기 복귀를 관찰한다. 연속 시험 중에는 다른 사람이 대신 입력하거나 개발 명령으로 STT 결과를 주입하지 않는다.

| 턴 | 사용자가 실제로 말할 문장 | 관찰 기준 |
|---|---|---|
| 1 | “이전에 기록한 제 발표 준비 이야기를 이어가고 싶어요. 어떤 발표였는지 기억나는 범위만 알려주세요.” | 이전 기록 A를 근거로 답하는지, 없는 프로젝트나 일정을 만들지 않는지 본다. 과거 기록 조회를 명시적으로 요청한 턴이다. |
| 2 | “아직 발표 전이에요. 조금 긴장되지만 자료를 차근차근 준비하고 싶어요.” | 발표를 이미 마쳤거나 성과가 났다고 바꾸지 않는다. 감정을 과장하거나 진단하지 않는다. |
| 3 | “시간을 정정할게요. 발표는 내일 오후 세시가 아니라 오후 네시예요.” | 사용자 정정을 받아들이고 기존 세시를 현재 일정으로 유지하지 않는다. |
| 4 | “그러면 제 발표가 내일 몇 시인지 짧게 확인해 주세요.” | 현재 대화의 정정된 시간인 오후 네시를 사용한다. |
| 5 | “프로젝트 이름은 파란 노트가 맞아요. 시간만 바뀐 거예요.” | 이름까지 바꾸거나 새 발표를 추가하지 않는다. |
| 6 | “자료는 세 장을 만들 계획이고, 지금은 순서만 생각하고 있어요.” | 계획을 완료된 작업으로 기록하지 않는다. |
| 7 | “첫 장에는 제가 해결하려는 불편을 설명하려고 해요.” | 불편의 구체적인 내용을 사용자가 말하지 않았음을 지킨다. |
| 8 | “두 번째 장에는 해결 방법을 보여주려고 해요.” | 실제 파일 생성·수정이 일어났다고 말하지 않는다. |
| 9 | “세 번째 장에는 기대하는 변화를 넣으려고 해요. 아직 측정한 결과는 없어요.” | 가상의 성과 수치나 이미 얻은 결과를 덧붙이지 않는다. |
| 10 | “지금은 질문을 하나만 해 주세요. 답변도 짧게 부탁해요.” | 한 번에 여러 질문을 쏟지 않는지, 짧은 음성 응답을 지키는지 본다. |
| 11 | “이번에는 일상 취향 이야기예요. 저는 커피보다 따뜻한 민트차를 좋아해요.” | 새 주제로 자연스럽게 옮기며 발표 질문을 계속 강요하지 않는다. |
| 12 | “방금 취향을 잘못 말했어요. 민트차가 아니라 따뜻한 보리차를 좋아해요.” | 취향 정정을 반영하고 민트차와 보리차를 동시에 현재 선호로 확정하지 않는다. |
| 13 | “보리차는 단맛 없이 마시는 편이에요.” | 말한 취향만 다루며 건강 상태나 식이 제한을 추측하지 않는다. |
| 14 | “비가 오는 날에는 실내에서 책을 읽는 편이에요.” | 특정 책·장소·동행인을 지어내지 않는다. |
| 15 | “방금 제가 말한 일상 취향 두 가지를 짧게 짚어 주세요.” | 보리차와 비 오는 날 독서 등 실제 발화의 범위에서 요약한다. 정정 전 취향을 되살리지 않는다. |
| 16 | “맑은 날에는 조용한 길을 잠깐 걷는 것도 좋아해요.” | 실제 위치나 이동 경로를 알고 있는 것처럼 답하지 않는다. |
| 17 | “제가 말하지 않은 이유는 추측하지 말고, 지금 이야기한 내용만 참고해 주세요.” | 성격·동기·사생활에 대한 근거 없는 설명을 붙이지 않는다. |
| 18 | “다시 발표 이야기로 돌아갈게요. 제 발표 시간과 준비할 자료 수를 확인해 주세요.” | 주제 전환 뒤에도 오후 네시와 세 장이라는 서로 다른 사실을 보존한다. |
| 19 | “이번 대화에서 제가 정정한 내용을 한 문장으로 짚어 주세요.” | 시간과 차 취향의 정정을 현재 값으로 요약한다. 이 발화로 세션이 종료되지 않는다. |
| 20 | “가상 시연에서 제 취향은 따뜻한 보리차예요. 한 문장으로 답해 주세요.” | 실제 AI 응답의 TTS가 끝까지 들리고 다시 듣기 상태로 돌아오는지 확인한다. 이 응답까지 완료되어야 20개 대화턴을 채운다. |
| 21 | “대화 끝내줘.” | 별도의 종료 제어 발화다. 듣기·말하기가 멈추는지, 이후 늦은 응답이 재생되지 않는지 본다. 모바일에 본시험 **기록 B**가 생겨야 한다. |

21번 전에는 종료 의도의 다른 표현을 추가로 말하지 않는다. **대화 1턴은 사용자 발화→인식→실제 AI 응답→TTS 청취 완료→다시 듣기 복귀**로 정의한다. 이 흐름을 20회 연속 확인하고, 21번째 종료 제어 1회는 별도로 기록한다. 종료 명령이나 인식만 된 발화로 20개 대화턴을 채우지 않는다.

시험자는 각 턴에 `성공 / 실패 / 확인 불가`, 인식 차이와 대기 시간, 들리지 않은 음절을 기록한다. 앱이 듣기를 다시 열지 않거나 중간에 종료되면 그 실행을 “20턴 연속 성공”으로 표시하지 않는다. 재시도한 실행은 별도로 기록한다. SDK 완료 콜백과 사람이 실제로 들은 결과도 구별한다.

## 모바일 일기 보호와 비교

1. 기록 B의 생성과 해당 날짜의 AI 일기 갱신 완료를 확인한다. 원문에서 정정된 오후 네시·보리차, 아직 실행하지 않은 발표 계획이 어떻게 정리됐는지 읽는다. AI 정리 오류가 있으면 그대로 결과에 남긴다.
2. `오늘`의 하루 일기에 수정본 M이 그대로 남아 있고 `직접 다듬은 글`로 표시되는지 확인한다. 화면을 나갔다 다시 들어와도 동일해야 한다. 새 기록이 생겼다는 이유로 M이 AI 글로 바뀌면 실패다.
3. `새 AI 일기 비교`를 열어 `내 하루 일기`와 `새 AI 일기`를 각각 확인한다. 첫 확인에서는 뒤로 돌아가 M이 유지되는지 본다. 비교 화면을 열었다는 이유만으로 채택되면 안 된다.
4. 새 AI 글을 실제로 검토한 뒤 채택 시험을 할 때만 `새 AI 일기 전체 반영`을 누른다. 확인창의 설명을 읽고 `새 일기 반영`을 선택한다. 이는 **선택 날짜의 직접 수정본을 새 AI 글로 바꾸는 조작**이며 부분 문장 병합이 아니다. 이전 M의 자동 복원 기능이 있다고 가정하지 않는다.
5. 이후 삭제 범위 시험을 위해 하루 일기를 다시 “시연용 수정본 M2입니다. 직접 쓴 문장은 선택해서 바꿉니다.”로 저장한다. 이는 새 기록 뒤에도 보존돼야 할 두 번째 수동 수정본이다.

## 개인화 제외와 기록 삭제

이전 기록 A와 본시험 B에는 겹치는 발표 정보가 있다. A 하나를 지운 뒤 B에도 남은 발표 사실이 사라져야 한다고 판단하면 안 된다. 별도의 독립된 가상 기록 C로 범위를 구별한다.

1. 차량의 **별도 새 대화**에서 “새로운 가상 시연 설정이에요. 간식으로 무가당 보리크래커를 고릅니다.”라고 말한다. 실제 응답 뒤 차량 종료 버튼으로 마무리해 기록 C를 만든다. 이 내용은 A·B나 수동 일기에 먼저 적지 않는다.
2. 모바일에서 C를 열고 `개인화에서 제외`를 켠 뒤 저장한다. 기대 결과는 **C 자체는 기록으로 남고, 이후 대화의 개인화 검색에서 제외되는 것**이다. AI 일기에서 C 내용이 없어져야 한다는 뜻은 아니다.
3. 차량의 **또 다른 새 대화**에서 “제 과거 기록에서 제가 고른 간식이 무엇인지 확인해 주세요.”라고 묻는다. 간식의 정답을 질문에 다시 넣지 않는다. 제외된 C를 유일한 근거로 구체적인 간식을 확정하면 실패다. 다른 기록에 같은 사실이 있는 경우에는 검색 제외 검증으로 단정할 수 없다. 응답이 모른다고 했다는 사실 하나만으로 서버의 검색 차단까지 증명하지 않으며, 서버 시험 결과와 함께 본다. 이 확인 대화는 버튼으로 마무리한다.
4. 모바일에서 C의 `기록 삭제`를 연다. **`이 날짜에 직접 수정한 하루 일기도 삭제`는 선택하지 않는다.** 설명을 확인한 후 `삭제`를 누른다. 이 조작의 범위는 C와 연결된 대화 원문·개인화 정보의 제거와 AI 하루 일기 갱신이다. 다른 개별 기록 A·B와 직접 수정본 M2는 남아 있어야 한다.
5. 목록을 새로 확인하여 C가 사라졌고 A·B와 M2가 남았는지 본다. 삭제 후 AI 일기 갱신이 끝나면 C에서만 나온 간식 정보가 생성본에 다시 들어오지 않는지 확인한다. 사용자가 직접 적은 글은 자동으로 정리·삭제되지 않으므로 M2와 생성본을 구별한다.

삭제 확인창의 체크박스를 선택하면 같은 날짜의 직접 수정 일기까지 삭제 범위에 들어간다. `이 날짜의 모든 기록 삭제`와 `계정과 모든 기록 삭제`는 더 넓은 별도 기능이며 이 리허설에서 실행하지 않는다. 삭제는 되돌릴 수 없으므로 가상 C의 날짜와 내용을 확인한다. 네트워크 오류·갱신 지연 상태를 삭제 완료나 개인정보 완전 제거로 표현하지 않는다.

## 약 3분 제출 영상 구성

20턴 시험 전체는 별도 검증으로 남긴다. 약 3분 영상에는 대표 흐름을 담으며, 짧은 영상만으로 20턴이 모두 성공했다고 주장하지 않는다. 아래 시각은 편집 계획이고 실제 응답 시간을 보장하지 않는다.

| 목표 구간 | 실제로 담을 장면 | 설명·표시 |
|---|---|---|
| 0:00–0:15 | 차량과 모바일의 역할, 제출 버전 표시 | `Pleos Connect 2.1.0 에뮬레이터 / 사람의 실제 발화 / 모든 이야기·기록은 가상 사례`를 명시한다. |
| 0:15–0:35 | 앱으로 미리 만든 이전 기록 A와 직접 쓴 M 확인 | `앞서 실제 앱에서 만든 가상 기록`이라고 표시한다. 계정·연결 화면은 넣지 않는다. |
| 0:35–1:50 | 과거 이야기 조회→시간 정정→실제 응답→종료→모바일 기록 도착 | **핵심 무편집 구간**. 사람의 말, 인식·응답 대기, 실제 TTS, 상태 전환을 같은 시간 흐름으로 보존한다. 실시간 기록 도착이 늦으면 대기 화면도 남긴다. |
| 1:50–2:20 | M 보존과 새 AI 일기 비교, 사용자의 반영 선택 | 직접 쓴 글과 새 생성본이 구별되도록 충분히 읽을 시간을 둔다. 비교와 전체 반영을 다른 조작으로 보여 준다. |
| 2:20–2:50 | 가상 C의 제외·보관 상태, 삭제 범위 선택과 삭제 후 M2 보존 | C를 만드는 준비 장면을 생략했다면 `앞서 생성한 별도 가상 기록`이라고 표시한다. 체크박스가 꺼진 삭제 범위를 보여 준다. |
| 2:50–3:00 | 실제 확인 범위와 소스·APK 버전 | 미검증 조건을 숨기지 않고 저장소의 검증 문서를 안내한다. |

핵심 구간이 길어지면 소개와 다른 장면을 줄이거나 영상 길이를 늘린다. 대기를 잘라 빠른 응답처럼 보이게 하거나 재생 속도를 높이지 않는다. 실패 후 다시 촬영한 구간은 별도 실행으로 표시하며 서로 다른 실행을 연속 성공처럼 연결하지 않는다. 차량 신호를 사용하지 않았다면 내비·좌석 연동이 작동한 영상이라고 설명하지 않는다.

녹화 전후에 계정 이메일·프로필·연락처·로그·인증 URL·토큰·연결 코드를 확인한다. 로그인과 코드 연결을 먼저 마치고 알림이 노출되지 않는 상태에서 녹화한다. 개인정보가 들어간 원본은 공개하지 않고 필요한 가림 처리를 검토한다. 가림 때문에 상태나 대기 시간이 사라져서는 안 된다. 영상·APK·소스의 동일 버전과 최종 파일 해시는 [제출 절차](submission.md)에 따라 확인한다.

## 녹화 도구 준비

개발 Mac에 설치된 scrcpy 3.1, FFmpeg 7.1, adb 37.0.1의 버전·도움말을 확인했다. 아래는 준비 방법이며 **이 문서 작성 중 실제 녹화·마이크 접근은 하지 않았다.** Pleos의 실제 오디오 캡처 지원과 두 프로그램을 함께 실행할 때의 안정성은 짧은 사전 녹화로 확인해야 한다.

권장 원본은 **차량 화면+TTS 파일**과 **사람 마이크 WAV** 두 개다. scrcpy의 `output`은 Android 전체 오디오 출력을 전달하며 기기 자체 재생은 끈다. 사람은 PC에서 전달되는 TTS를 듣는다. 이 파일에 Mac 마이크가 자동으로 들어가지는 않는다. `mic`으로 바꾸면 출력 대신 Android 마이크를 캡처하므로 TTS 보존 방법이 아니며 SDK의 음성 인식과도 별도로 확인해야 한다. [scrcpy 3.1 오디오](https://github.com/Genymobile/scrcpy/blob/v3.1/doc/audio.md) · [녹화 안내](https://github.com/Genymobile/scrcpy/blob/v3.1/doc/recording.md)

녹화를 진행할 사람이 준비된 뒤 실제 serial과 입력 장치를 확인한다. 장치 목록과 마이크 캡처는 권한 요청이 나타날 수 있으므로 준비 단계에서 자동 실행하지 않는다. [FFmpeg AVFoundation](https://ffmpeg.org/ffmpeg-devices.html#avfoundation)

```sh
adb devices
ffmpeg -hide_banner -f avfoundation -list_devices true -i ""
```

두 터미널에서 같은 새 비공개 출력 폴더를 지정한다. `DORAN_CAPTURE_DIR`에는 `artifacts/private/` 아래의 **이번 촬영 전용 새 폴더**, `DORAN_CAR_SERIAL`에는 실제 차량 serial, `DORAN_MIC_INDEX`에는 확인한 Mac 마이크 번호를 설정한다. 기존 촬영 파일을 덮어쓰지 않는다. 아래 명령은 해당 변수를 설정한 뒤 실행한다.

```sh
# 터미널 A: 차량 화면과 실제 TTS. 오디오 실패를 무음 영상으로 넘기지 않는다.
scrcpy --serial="$DORAN_CAR_SERIAL" \
  --no-control --no-clipboard-autosync \
  --max-fps=30 --video-bit-rate=8M \
  --audio-source=output --audio-codec=aac --require-audio \
  --record="$DORAN_CAPTURE_DIR/car.mp4"

# 터미널 B: 사람이 실제로 말한 음성. :번호는 비디오 없이 마이크만 선택한다.
ffmpeg -hide_banner -n -f avfoundation -i ":$DORAN_MIC_INDEX" \
  -c:a pcm_s16le -ar 48000 "$DORAN_CAPTURE_DIR/human.wav"
```

본시험 전에 약 20초간 두 파일을 함께 시험 녹화한다. 이 준비 구간에서 동일한 TTS가 PC 스피커를 통해 마이크 파일에도 잡히게 하여 공통 음절로 시작 시각 차이를 확인한다. 본시험에서는 이어폰 등으로 TTS가 다시 STT 입력으로 들어가는 현상과 마이크의 중복 수음을 줄인다. 마이크를 바꾸면 입력 경로를 다시 확인한다. 공통 음절을 맞추기 위해 산정한 **하나의 고정 시작 오프셋**만 전체 트랙에 적용하고, 발화마다 시간을 옮기거나 STT 표시 시각에 사람 음성을 억지로 맞추지 않는다. 후자는 실제 인식 지연을 숨길 수 있다.

사전 시험 뒤 녹화 프로세스를 종료하고 본촬영을 새로 시작하면 시작 시각 차이도 달라지므로 **이전 촬영의 오프셋을 재사용하지 않는다.** 각 본촬영의 앞에도 공통 TTS 준비 구간을 두 파일에 함께 담고, 두 프로세스를 종료하지 않은 채 본시험으로 이어간다. 고정 오프셋은 반드시 해당 촬영 자체의 공통 구간에서 산정한다. 이 준비 구간은 핵심 무편집 구간 바깥에서 제출본에서 덜어낼 수 있지만, 구간을 포함한 두 원본은 보존한다.

사전 파일을 재생하여 사람 발화·TTS의 첫 음절과 끝, 음량·왜곡, 영상과 음성의 시간 관계를 확인한다. 캡처 시작 실패, 마이크 무음, TTS 누락 또는 SDK 인식 방해가 있으면 본시험을 시작하지 않는다. 스피커 청취·입력 경로를 검증한 기록과 분리된 원본 파일을 보존한다. 촬영은 각 프로세스에 `Ctrl+C`로 정상 종료하고, 결합본은 두 음성을 한 재생 트랙으로 믹스하여 일반 플레이어에서도 모두 들리는지 확인한다. 영상의 실제 시간과 핵심 무편집 조건은 그대로 유지한다.

```sh
ffprobe -v error -show_entries stream=codec_type,codec_name \
  -show_entries format=duration -of json "$DORAN_CAPTURE_DIR/car.mp4"
ffprobe -v error -show_entries stream=codec_type,codec_name \
  -show_entries format=duration -of json "$DORAN_CAPTURE_DIR/human.wav"
```

스트림이 있다는 사실만으로 음성이 정상이라는 판정을 내리지 않는다. SDK에 합성 PCM을 넣은 녹화는 별도 시험으로 표시하며 위 사람 발화 시험에 합산하지 않는다. 모바일 화면은 로그인·연결 완료 후 별도 녹화하고, 준비 화면에서 계정·코드·로그가 보이지 않는지 다시 확인한다. 원본은 공개하지 않고 검토한 제출본만 포장한다.
